Instruction : le skill ticket-scope. Ce document se déclenche quand je demande à l'agent de travailler sur un ticket précis : avant de toucher un seul fichier, il va lire le skill pour vérifier qu'il reste dans le périmètre du ticket, sauf si un bug bloquant justifie d'en sortir. Je l'ai testé en session fraîche avec une formulation naturelle ("occupe-toi du ticket 7"), sans jamais utiliser les mots de la description, et le skill s'est bien chargé avant la première modification. Il ne se déclenche pas quand la tâche n'est pas une implémentation : j'ai posé une question pure sur le fonctionnement de l'authentification par cookie, sur le même domaine (comptes, sessions), et le skill n'a jamais été lu.

Enforcement : le hook qui bloque git commit et git push. Ce hook empêche l'agent d'exécuter lui-même une commande git commit ou git push, sous n'importe quelle forme (avec -m, --force, etc.) — c'est toujours moi qui commit, après avoir relu les changements. Une simple instruction ne suffisait pas : j'avais déjà dû répéter "ne commit pas, ne push pas" dans quatre sessions différentes, dont une tournait sans aucune protection technique, et ça a marché quatre fois sur quatre uniquement parce que je l'avais réécrit à chaque fois. Rien ne garantit qu'une cinquième fois se passe aussi bien, et un commit non désiré coûte plus cher à réparer qu'à empêcher. La preuve la plus parlante : quand j'ai demandé à l'agent de committer, il a refusé tout seul en expliquant qu'un hook l'en empêchait — mais ça restait juste une anticipation, pas une preuve. Il a fallu que je le force explicitement à essayer pour voir le hook agir réellement et bloquer la commande.
